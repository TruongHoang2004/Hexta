# Agentic Memory System

Start with [AGENTS.md](../AGENTS.md), then [the epic index](epics/README.md), the relevant epic README and its latest session. Consult the [canonical system-design index](designs/2026-10-18_system-design_design.md) for architecture. Root AGENTS.md contains the shared rules; GEMINI.md redirects to it. The system pack covers product decisions, architecture, existing/target DB, HTTP, gRPC/AI, Kafka, concurrency and operations. Older dated designs remain historical evidence.

A repository-level storage system for tracking the AI assistant's memory, reasoning processes, execution plans, technical designs, code reviews, changelogs, and development rules directly within the codebase.

---

## 1. Directory Structure

```text
agentic-memory/
├── epics/          # Per-epic context, status, acceptance and separate session records
├── plans/          # Implementation plans, task breakdown, risk analysis
├── designs/        # Technical specifications, architecture, DB schemas, API contracts
├── reviews/        # Code quality audits, security checks, performance analysis
├── CHANGELOG.md    # Consolidated changelog, release milestones, and system evolution
└── rules/          # Engineering guidelines, coding standards, architectural invariants
```

---

## 2. File Naming Conventions

All documents generated by the agent must adhere to the standardized naming format:

- **Plans**: `agentic-memory/plans/YYYY-MM-DD_<feature-name>_plan.md`
- **Designs**: `agentic-memory/designs/YYYY-MM-DD_<feature-name>_design.md`
- **Reviews**: `agentic-memory/reviews/YYYY-MM-DD_<feature-name>_review.md`
- **Changelogs**: Consolidated in `agentic-memory/CHANGELOG.md`
- **Rules**: `agentic-memory/rules/<rule-topic>.md` (e.g., `development-rules.md`, `security-standards.md`)

*Note: `YYYY-MM-DD` denotes the creation date, and `<feature-name>` is lowercase separated by hyphens (`-`).*

## 3. Standard Document Formats

### 3.1 Plans (`plans/`)
- **Objective & Scope**: Description of business requirements and engineering goals.
- **Current State Analysis**: Existing architecture, impacted paths, and constraints.
- **Step-by-Step Task Breakdown**: Ordered list of implementation steps and affected files.
- **Risk Assessment & Edge Cases**: Potential failure points, edge cases, and mitigation strategies.
- **Definition of Done (DoD)**: Acceptance criteria and test coverage requirements.

### 3.2 Designs (`designs/`)
- **System Architecture**: High-level component interactions and Mermaid sequence/flow diagrams.
- **Database Schema**: Table definitions, migration strategy (Atlas / GORM), relationships, and indexes.
- **API Contracts**: Routes, HTTP verbs, request/response DTOs, and Swagger doc tags.
- **Security & Performance**: Auth verification, Redis caching strategy, transactions, and concurrency safeguards.

### 3.3 Reviews (`reviews/`)
- **Overview**: Summary of reviewed commits, PRs, or file changes.
- **Standards Adherence (`rules/` & `AGENTS.md`)**: Layered architecture, error handling, strict typing, framework patterns.
- **Security**: OAuth state CSRF checks, injection defenses, token leakage avoidance, session lifetimes.
- **Performance & Reliability**: N+1 queries, race conditions, resource leaks, context timeouts.
- **Actionable Remediation**: Specific code snippets and corrective recommendations.

### 3.4 Changelogs (`CHANGELOG.md`)
- **Consolidated Format**: High-density historical reference summarizing changes, technical decisions, impacted paths, and verification steps by milestone/domain.
- **Append on Completion**: New release notes and feature completions are appended directly into `agentic-memory/CHANGELOG.md` instead of creating dispersed files.

### 3.5 Rules (`rules/`)
- Living documentation of engineering standards agreed upon by the team and AI assistants.
- Rules become effective when loaded through the repository entry instructions; not every Markdown file is automatically read. Consult the relevant rules explicitly.
- **Language Standard**: All documents, commit messages, comments, and code in this repository must be written in **English**.


## Epic and session storage

Each epic is a directory under `epics/` with a README containing status/completed, scope, decisions, acceptance checklist, references, session links and next work. Session records live separately under its `sessions/YYYY-MM-DD_<topic>.md`; use `epics/_SESSION_TEMPLATE.md`. The epic index contains only navigation/status, and SESSION_CONTEXT.md is a legacy redirect.

Keep global engineering rules in AGENTS.md, cross-domain architecture in designs/system, and execution history in the relevant epic. Do not consolidate sessions back into one growing context file. A completed session does not imply a completed epic; for delivered code/docs, mark done/completed:true only after scoped acceptance and confirmed merge. Shared CHANGELOG.md remains a release/change ledger, not a substitute for per-epic session context.
